# multipart_payload_last

Category: multipart | Risk: standard | Applies to: aws+cloudflare+akamai | Fidelity: transparent

> **Impact:** **Impact: guaranteed.** Once this transform delivers, a conforming
origin has interpreted the ORIGINAL payload byte-for-byte - the
exploit lands regardless of application stack.

## Mechanism
The transform reverses the order of multipart parts so the attacker-controlled part lands last. Combined with padding transforms such as pad_multipart_decoy, the payload sits past the size-window cutoff. Each part stays byte-identical.

## Why the WAF misses it
Body inspection stops at the configured window (8 KB default on Akamai Kona; 8 KB fixed on AWS ALB/AppSync; 128 KB or less on Cloudflare). Parts ordered after the padding fall outside the scanned slice, so their content never reaches the signature engine.

## Why the origin still accepts it
A conforming parser walks delimiters to the final boundary regardless of part order. Named-field semantics stay unchanged because each part keeps its own headers and name.

## Wire example

Generated by applying this transform to a representative request (fidelity tier: **transparent**).

Original:

```http
POST /upload HTTP/1.1
Host: shop.test
Content-Type: multipart/form-data; boundary=B2
Content-Length: 127

--B2
Content-Disposition: form-data; name="first"

one
--B2
Content-Disposition: form-data; name="second"

two
--B2--

```

After `multipart_payload_last`:

```http
POST /upload HTTP/1.1
Host: shop.test
Content-Type: multipart/form-data; boundary=B2
Content-Length: 127

--B2
Content-Disposition: form-data; name="second"

two
--B2
Content-Disposition: form-data; name="first"

one
--B2--

```

## Prerequisites and limits
- Alone, reordering only helps when another transform pushes earlier parts past the cutoff.
- Applications that assume a fixed field order see the reversed sequence.
- File-count and total-size limits on the origin can reject the padded body.
