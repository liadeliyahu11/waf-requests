# header_pad_early

Category: headers | Risk: standard | Applies to: aws+cloudflare+akamai | Fidelity: transparent

> **Impact:** **Impact: guaranteed.** Once this transform delivers, a conforming
origin has interpreted the ORIGINAL payload byte-for-byte - the
exploit lands regardless of application stack.

## Mechanism
The transform injects about ten benign padded headers totalling just under the assumed header-inspection budget, default 7000 bytes, ahead of the existing headers. The default sits under the measured caps of roughly 8 KB total and 200 headers per request. Payload-bearing headers then land outside the inspected window.

## Why the WAF misses it
AWS WAF measured in prior repo work (`research/cve-2021-44228-waf/README.md`) truncates Headers(ALL) inspection at about 8 KB or 200 headers. Padding benign headers ahead of a payload-bearing header pushes that header past the truncation point, so its content never reaches signature matching. This was a measured bypass before AWS added per-header inspection arms.

## Why the origin still accepts it
The origin web server reads every header regardless of any WAF-side window; no such truncation exists in the application stack. The payload header arrives intact and the framework processes it normally.

## Prerequisites and limits
- Fails against per-header inspection arms, which AWS added after this class was demonstrated.
- Fails when origin or intermediary header-count or size limits reject the padded request.
- Padded headers are visible in logs; defenders can learn the pattern.
- The assumed budget is an estimate. Measure the real cap with live probes before relying on exact offsets.
