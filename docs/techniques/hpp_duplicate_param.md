# hpp_duplicate_param

Category: hpp | Risk: standard | Applies to: aws+cloudflare+akamai | Fidelity: differential

> **Impact:** **Impact: conditional.** The wire payload DIFFERS from the original;
the origin interprets it correctly only if its parser behaves as
documented here. Delivery alone is not exploitation - prove it with
`python -m waf_requests verify <url>`.

## Mechanism
For every query parameter the transform emits a benign duplicate first, then the original pair. The wire form reads `q=1&q=payload`. Both pairs stay well-formed.

## Why the WAF misses it
Many WAF variable extractors take the first occurrence of a parameter name for signature matching. They inspect `q=1`, see nothing malicious, and never evaluate the second occurrence.

## Why the origin still accepts it
Last-wins frameworks fold repeated names into one value and keep the final occurrence. The application reads `payload` from `q`. This is the classic HTTP Parameter Pollution differential described by OWASP.

## Wire example

Generated by applying this transform to a representative request (fidelity tier: **differential**).

Original:

```http
GET /search?q=%27%20OR%20%271%27%3D%271 HTTP/1.1
Host: shop.test
User-Agent: exploit/1.0
```

After `hpp_duplicate_param`:

```http
GET /search?q=1&q=%27%20OR%20%271%27%3D%271 HTTP/1.1
Host: shop.test
User-Agent: exploit/1.0
```

## Prerequisites and limits
- Fails against first-wins frameworks; the payload then arrives as the benign duplicate.
- Fails when the WAF matches all occurrences.
- Applications that iterate all pairs see both values and may reject the ambiguity.
