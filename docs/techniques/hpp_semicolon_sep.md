# hpp_semicolon_sep

Category: hpp | Risk: standard | Applies to: aws+cloudflare+akamai | Fidelity: differential

> **Impact:** **Impact: conditional.** The wire payload DIFFERS from the original;
the origin interprets it correctly only if its parser behaves as
documented here. Delivery alone is not exploitation - prove it with
`python -m waf_requests verify <url>`.

## Mechanism
The transform replaces `&` separators with `;` between query pairs. The wire form reads `q=1;q=payload`. To a scanner that splits only on `&`, the whole string looks like one opaque parameter.

## Why the WAF misses it
Variable extractors that split on `&` only produce one parameter whose value is `1;q=payload`. Signatures anchored on parameter values do not match across that blob, so the payload inside stays uninspected.

## Why the origin still accepts it
Frameworks with historic PHP or JSP lineage split query strings on `;` as well as `&`. On those stacks the pairs decode normally and the application reads the payload value. This differential depends on origin separator support.

## Wire example

Generated by applying this transform to a representative request (fidelity tier: **differential**).

Original:

```http
GET /s?a=1&q='+OR+'1'='1 HTTP/1.1
Host: shop.test
```

After `hpp_semicolon_sep`:

```http
GET /s?a=1;q=%27%2BOR%2B%271%27%3D%271 HTTP/1.1
Host: shop.test
```

## Prerequisites and limits
- Conditional in practice: frameworks that accept only `&` see one malformed pair, not two parameters.
- WAFs that also split on `;` defeat it.
- Applications receive different parameter counts depending on their own splitting rules; verify per target.
- RFC 3986 reserves `;` inside segments but does not define query-pair separation, so behavior is stack-specific.
