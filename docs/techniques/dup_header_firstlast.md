# dup_header_firstlast

Category: headers | Risk: standard | Applies to: aws+cloudflare+akamai | Fidelity: differential

> **Impact:** **Impact: conditional.** The wire payload DIFFERS from the original;
the origin interprets it correctly only if its parser behaves as
documented here. Delivery alone is not exploitation - prove it with
`python -m waf_requests verify <url>`.

## Mechanism
The transform duplicates a security-relevant header such as User-Agent or Referer: a benign value goes first, the original value second. The two occurrences carry different contents by design.

## Why the WAF misses it
Inspection components differ in which occurrence they read: some take the first, some the last, some concatenate. When the matcher reads the benign first value while the origin reads the last, signatures bound to that field see nothing malicious.

## Why the origin still accepts it
RFC 9110 section 5.2 defines combined semantics for repeated fields but real stacks diverge in reading order. Whichever component wins, this page documents the ambiguity as an educational demonstration of differential parsing rather than a guaranteed bypass.

## Wire example

Generated by applying this transform to a representative request (fidelity tier: **differential**).

Original:

```http
GET /search HTTP/1.1
Host: shop.test
User-Agent: <script>alert(1)</script>
```

After `dup_header_firstlast`:

```http
GET /search HTTP/1.1
Host: shop.test
User-Agent: Mozilla/5.0 (X11; Linux x86_64) waf_requests-education
User-Agent: <script>alert(1)</script>
```

## Prerequisites and limits
- The winner depends on stack reading order on both sides. Measure per target; there is no guarantee.
- Strict intermediaries reject or merge duplicate fields.
- Some stacks join duplicate values with a comma, producing a combined string both sides can match against.
