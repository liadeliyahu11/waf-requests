# spoof_trusted_ip

Category: headers | Risk: conditional | Applies to: aws+cloudflare+akamai | Fidelity: differential

> **Impact:** **Impact: conditional.** The wire payload DIFFERS from the original;
the origin interprets it correctly only if its parser behaves as
documented here. Delivery alone is not exploitation - prove it with
`python -m waf_requests verify <url>`.

## Mechanism
Sets `X-Forwarded-For: 127.0.0.1`, `CF-Connecting-IP: 127.0.0.1`, and `True-Client-IP: 127.0.0.1` on the outgoing request.

## Why the WAF misses it
Edges that derive client identity for IP reputation, allowlists, or rate-limit keys from INBOUND instances of these headers read the injected loopback value. Requests then ride trusted/private-IP rules instead of the attacker's reputation bucket.

## Why the origin still accepts it
The application receives whatever header set the edge forwards; when the edge passed the request through unmodified, app-side IP logging and checks see 127.0.0.1 too - which is exactly the misconfiguration being demonstrated.

## Wire example

Generated by applying this transform to a representative request (fidelity tier: **differential**).

Original:

```http
GET /search HTTP/1.1
Host: shop.test
User-Agent: <script>alert(1)</script>
```

After `spoof_trusted_ip`:

```http
GET /search HTTP/1.1
Host: shop.test
User-Agent: <script>alert(1)</script>
X-Forwarded-For: 127.0.0.1
CF-Connecting-IP: 127.0.0.1
True-Client-IP: 127.0.0.1
```

## Prerequisites and limits
- Correctly configured edges OVERWRITE these headers at the socket and log the real peer - there the transform only adds traceable noise.
- Cloudflare strips inbound `CF-Connecting-IP`; AWS WAF has no native trust in it unless custom rules read it.
- Rate-limit keys derived from a spoofable header are the realistic win case.
