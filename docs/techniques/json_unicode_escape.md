# json_unicode_escape

Category: unicode | Risk: standard | Applies to: aws+cloudflare+akamai | Fidelity: transparent

> **Impact:** **Impact: guaranteed.** Once this transform delivers, a conforming
origin has interpreted the ORIGINAL payload byte-for-byte - the
exploit lands regardless of application stack.

## Mechanism
The transform rewrites JSON string values, escaping significant ASCII characters (`" \ < > ( ) ' ; & |` and control characters) as `\uXXXX` sequences. The JSON document stays structurally identical; only the spelling of characters inside strings changes.

## Why the WAF misses it
Naive regex scanners match literal byte sequences such as `<script>` inside the body. After escaping, those bytes exist only as `\u003cscript\u003e`, and the anchors the rules rely on are gone. Scanners that do not run a full JSON decode cannot see through the escapes.

## Why the origin still accepts it
Any RFC 8259 parser decodes `\uXXXX` escapes during tokenization and yields identical string values to the unescaped form. The application receives exactly the payload the sender intended.

## Wire example

Generated by applying this transform to a representative request (fidelity tier: **transparent**).

Original:

```http
POST /search HTTP/1.1
Host: shop.test
Content-Type: application/json
Content-Length: 20

{"q": "' OR '1'='1"}
```

After `json_unicode_escape`:

```http
POST /search HTTP/1.1
Host: shop.test
Content-Type: application/json
Content-Length: 39

{"q":"\u0027 OR \u00271\u0027=\u00271"}
```

## Prerequisites and limits
- Loses against WAFs that parse JSON fully before matching, because decoding restores the literals.
- The escape set is fixed. Signatures anchored on characters outside the set survive untouched.
- Escaping control characters changes nothing semantically but grows the body slightly.
