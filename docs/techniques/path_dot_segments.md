# path_dot_segments

Category: path | Risk: standard | Applies to: aws+cloudflare+akamai | Fidelity: differential

> **Impact:** **Impact: conditional.** The wire payload DIFFERS from the original;
the origin interprets it correctly only if its parser behaves as
documented here. Delivery alone is not exploitation - prove it with
`python -m waf_requests verify <url>`.

## Mechanism
The transform prefixes percent-encoded dot-segments - `/%2e/waf/%2e%2e` - to the path. Raw `/./` and `/../` are stripped by client-side URL preparation (measured: `requests` removes them before sending, a silent no-op), so the encoded form is the only one that reaches the wire. A conformant edge or origin that decodes unreserved escapes and then applies RFC 3986 remove_dot_segments computes exactly the original path.

## Why the WAF misses it
Path-scoped rules anchor on the literal path string as received. Before decoding, `/%2e/waf/%2e%2e/search` shares no characters with an anchored `/search` condition. Engines that match before decoding - or normalize in a different order than the origin router - see a different string.

## Why the origin still accepts it
Routers decode the request-target, then resolve dot segments per RFC 3986 before dispatch: `/%2e/waf/%2e%2e/search` becomes `/./waf/../search`, which normalizes to `/search`. The handler sees the same effective path as an untransformed request.

## Wire example

Generated by applying this transform to a representative request (fidelity tier: **differential**).

Original:

```http
GET /search?q=%27%20OR%20%271%27%3D%271 HTTP/1.1
Host: shop.test
User-Agent: exploit/1.0
```

After `path_dot_segments`:

```http
GET /./waf/../search?q=%27%20OR%20%271%27%3D%271 HTTP/1.1
Host: shop.test
User-Agent: exploit/1.0
```

## Prerequisites and limits
- Wins only where the router normalizes but the signature engine does not.
- A WAF that normalizes the path before matching defeats it.
- Routers that treat dot segments literally return 404.
