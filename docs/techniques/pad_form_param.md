# pad_form_param

Category: size | Risk: standard | Applies to: aws+cloudflare+akamai | Fidelity: additive

> **Impact:** **Impact: guaranteed for the original fields.** Decoys are extra
distinct-name parameters/parts no exploit reads.

## Mechanism
The transform prepends one oversized urlencoded parameter named `waf_filler` before the existing query pairs in the body. The decoy value is sized so the assumed inspection window fills with decoy bytes. The real payload pairs sit past the cutoff.

## Why the WAF misses it
The scanner reads the body up to the configured limit (8 KB ALB/AppSync fixed for AWS; 16 KB default to 64 KB elsewhere on AWS; 128 KB or less on Cloudflare; 8 KB default on Akamai). That window now holds only the decoy parameter. The payload-bearing pairs fall outside it and never reach signature matching.

## Why the origin still accepts it
The decoy key is distinct from every payload key. Last-value-wins form parsers read each key independently, so the payload parameters keep their values. The extra `waf_filler` key is inert data the application ignores.

## Wire example

Generated by applying this transform to a representative request (fidelity tier: **additive**).
The inspection window is shrunk to 256 bytes here so
the pad geometry fits on screen.

Original:

```http
POST /search HTTP/1.1
Host: shop.test
Content-Type: application/x-www-form-urlencoded
Content-Length: 13

q=' OR '1'='1
```

After `pad_form_param`:

```http
POST /search HTTP/1.1
Host: shop.test
Content-Type: application/x-www-form-urlencoded
Content-Length: 281

waf_filler=<256x 'A'>&q=' OR '1'='1
```

## Prerequisites and limits
- Fails when the operator raised the inspection limit above the assumed profile value.
- Fails when a rule uses `oversize=match` on AWS, because the oversized body itself becomes the match signal.
- Applications that iterate all form fields see the extra `waf_filler` key. Strict field allowlists reject it.
- The decoy key name is fixed and visible in logs. Rotate it if defenders learn it.
